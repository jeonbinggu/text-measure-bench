# 결과 해석 (초안)

> **초안이다.** 아래 문장은 측정 결과를 옮겨 적은 관찰이며, 결론 문장은 사람이 검토해 확정한다.
> 표는 `npm run tables`가 `results/*.json`에서 만든 것이다. 손으로 고치지 않는다.

## 1. 질문

1. 박스 여러 개의 너비가 매 프레임 바뀔 때, 높이를 다시 재는 비용은 방식(DOM 읽기 / Canvas 측정 / pretext `layout`)에 따라 얼마나 다른가?
2. DOM을 읽지 않고 잰 높이는 브라우저가 실제로 레이아웃한 높이와 얼마나 일치하는가? 어떤 문자열에서 어긋나는가?
3. 같은 줄 배열을 HTML · SVG · Canvas에 그리면 서로 같은 자리에 그려지는가?

## 2. 측정 방법 요약

- 리사이즈: 박스 N개(10 / 60 / 200), 너비 320 → 640px, 30프레임, 조합마다 5회. 프레임마다 "측정 시작 ~ 높이 반영 완료"를 잰다.
- 오차: 케이스 8종 × 너비 3가지. 기준값은 DOM.
- 렌더링: pretext `layoutWithLines()`의 줄 배열 하나를 세 렌더러에 그려 3분할·겹쳐 보기로 비교.
- 자세한 조건과 한계는 [method.md](method.md).

## 4. 예상과 달랐던 점

표와 원본 JSON에서 읽은 관찰이다. 원인을 확인하지 못한 것은 그렇게 적었다.

1. **Canvas 방식이 DOM 방식보다 느리게 나왔다.** 세 N 모두에서 `canvas`의 프레임 시간이 `dom-batched`, `dom-interleaved`보다 컸다(위 표).
   이 Canvas 구현은 폭 캐시 없이, 끊을 수 있는 자리마다 후보 줄 전체를 `measureText`로 다시 잰다. 한글은 글자마다 끊을 수 있어서 호출 수가 글자 수만큼 된다.
   즉 이 수치는 "Canvas로 재면 느리다"가 아니라 "캐시 없는 단순 구현은 이만큼 든다"로 읽어야 한다. 폭 캐시를 두면 얼마나 줄어드는지는 재지 않았다(`미측정`).
2. **회차 사이의 변동이 컸다. 이 표의 절대값과 배율은 아직 믿을 만한 정밀도가 아니다.** 같은 조합의 회차별 중앙값이 회차에 따라 2~4배까지 달랐다(예: `results/resize-canvas-60-1.json` ~ `-5.json`의 프레임 중앙값을 비교해 볼 것). "가장 튀는 1회 제외"는 한 번 튄 값을 걸러 내는 규칙이라, 느린 회차와 빠른 회차가 섞여 있는 이런 분포는 정리해 주지 못한다.
   - 전체 측정을 두 번 돌렸다. 첫 번째(커밋 `cf4093f`에 원본이 남아 있다)에서는 1회차만 빠르고 2~5회차가 느렸고, 두 번째(지금 `results/`)에서는 3~4회차가 빠르고 1~2회차가 느렸다. 빨라지는 회차가 일정하지 않으므로 "첫 실행이라서"가 아니라 측정 중 기기 상태가 바뀐 것으로 보인다.
   - 측정은 배터리로 구동 중이고 Android Studio가 떠 있는 노트북에서 했다. CPU 전력 상태나 백그라운드 부하가 원인일 수 있지만 **확인하지 못했다.**
   - 그 와중에도 두 번의 측정, 모든 회차에서 같았던 것: N이 60 이상일 때 프레임 시간의 순서는 `pretext` < `dom-batched` < `dom-interleaved` < `canvas`였다.
   - 전원을 연결하고 다른 프로그램을 닫은 상태에서 다시 재야 한다. 그때까지 이 표는 "순서"까지만 읽는다.
3. **pretext는 42행 전부에서 DOM과 줄 수·높이·줄 내용이 같았다.** 이모지, 공백 없는 URL, 금칙 처리, 폴백 글리프, keep-all 모두 포함이다. 차이가 나는 케이스를 찾지 못했다는 뜻이지, 차이가 없다는 증명은 아니다(케이스 7종 × 너비 3 × 모드 2, Chromium 하나).
4. **폰트 로드 전후 값은 일부 너비에서만 달랐다.** `before-font` 표에서 높이가 바뀐 너비와 안 바뀐 너비가 섞여 있다. 폴백 폰트와 Pretendard의 글자 폭 차이가 줄 수를 바꿀 만큼 쌓이는 너비에서만 드러난다. 바뀐 너비에서는 pretext의 "로드 후 (그대로)" 값이 로드 전 값 그대로였고, 캐시를 비운 뒤에야 DOM과 같아졌다.
5. **렌더러 겹쳐 보기에서 폴백 글리프만 세로로 어긋났다.** Pretendard에 있는 글자(한글, 영문, 숫자)는 세 렌더러가 겹쳤고, 폴백 폰트로 그려진 한자·일부 기호는 HTML / SVG / Canvas가 서로 1px 안팎 위아래로 어긋나 보였다(`docs/img/view-overlay-fallback.png`).
   - 확인한 것(`node scripts/inspect-fonts.mjs`): 같은 한자 문자열의 폭은 세 렌더러가 같았고, HTML과 SVG가 실제로 쓴 글꼴도 같았다(Malgun Gothic). 그러므로 폭이나 글꼴 선택의 차이는 아니다.
   - 확인하지 못한 것: Canvas가 쓴 글꼴(브라우저가 알려 주지 않는다), 세로 어긋남의 원인. 후보는 폴백 글꼴의 ascent/descent 반올림 방식 차이, 힌팅에 의한 세로 스냅, 렌더러별 서브픽셀 위치 처리다. **확정하지 못했다.**
   - 고쳐서 맞추지 않았다.

## 6. 다음에 확인할 것

- 전원을 연결하고, 확장 프로그램이 없는 창에서 전체 측정을 다시 돌려 1회차 현상과 수치가 유지되는지.
- Canvas 측정에 폭 캐시를 넣은 구현을 **별도 방식으로 추가**해 같은 시나리오로 재기(기존 `canvas`는 그대로 두고 비교).
- 프레임 시간에 들어 있지 않은, 스크립트 뒤의 브라우저 레이아웃·페인트 비용을 DevTools Performance로 방식별로 확인.
- 다른 브라우저(Firefox, Safari)와 다른 OS에서의 오차 표. 폴백 폰트와 이모지 폰트가 달라진다.
- 폴백 글리프의 세로 어긋남 원인. 폴백 글꼴을 `font-family`에 명시했을 때도 어긋나는지.
- 편집(커서 · 선택 · IME), 확대 · 인쇄 품질 — 위 표의 `미확인` 칸.
